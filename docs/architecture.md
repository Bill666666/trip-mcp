# 架构

```text
MCP client
    ↓ stdio
server.ts（官方 SDK、输入 schema、工具声明）
    ↓
service.ts（按账号串行、任务生命周期、防重复提交）
    ├── store.ts（本地 JSON 原子落盘、账号文件锁）
    └── browser.ts（独立 Chromium 持久资料）
              ↓
adapters.ts（Ctrip / Trip Moments 页面适配）
              ↓
           平台网页
```

## 取舍

- 使用 TypeScript + Playwright，便于读 DOM、文件上传、浏览器集成测试。与参考项目的 Go + Rod 实现不同，业务分层思路相同。
- 发布工具实际驱动本地浏览器，不只向 AI 返回待执行脚本。
- 两站共用 MCP 工具，分开登录资料、入口、地点选择器、提交控制和结果识别。
- `stdio` 由客户端管理本地生命周期，无 HTTP 端口、中央服务、公共账号或维护者托管凭据。
- 当前只接受社区 HTTPS URL。限制域名、端口、路径和 URL 凭据；页面正文不被当作执行指令。
- 账号锁与串行队列分别处理跨进程、单进程并发。任务在点击提交之前写入 `submitting`，重启后不会自动重试。
- 准备任务包含精确内容指纹及页面签名；预览后修改表单需要重新准备。
- 查询结果明确标记有限滚动范围、无 URL 卡片以及摘要提取，避免把局部读取描述为全量。

## 已知边界

浏览器自动化受页面结构、登录过期、验证码和网络影响。未识别到控件或结果时返回错误/unknown。选择器需按平台更新；尤其国内发布页面仍需登录后校准。

单次查询不提供完整爬取。页面详情的评论、折叠段落不保证全量读取。标题关键词过滤不是平台全站搜索。

本地去重只能约束这个数据目录下的任务；换目录、手动发文、改文案或多个设备之间不能保证全局去重。发布前需核对账号槽位实际对应的用户，客户端应让用户查看预览截图。
